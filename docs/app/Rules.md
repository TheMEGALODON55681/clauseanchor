# Backend Rules

Standing rules for every backend phase. Read this file before starting any work. If a phase spec conflicts with this file, this file wins unless the phase spec says it overrides a named rule.

---

## 1. Repository and ownership

- This is a solo-developer codebase. All code, comments, docs and commit messages read as one person's work.
- **Zero AI attribution anywhere.** No "Claude", "Anthropic", "AI-generated", "generated by", "co-authored-by", "subagent", "assistant", model names or tool names in code, comments, docs, commit messages or file names. Before stopping at the end of any part, run:
  ```bash
  grep -rniE "claude|anthropic|co-authored|generated by|subagent|openai|gpt-|llm assistant" backend/ docs/app/ --exclude-dir=.venv --exclude-dir=graphify-out --exclude=Rules.md
  ```
  No output means clean. The excludes skip this file, which holds the pattern text, plus installed packages and generated graph output. Fix every hit that is not a false positive (for example a third-party package name).
- **You edit only `backend/` and `docs/app/`.** Never touch `ml/`, `frontend/`, `data/`, `.github/` or any root file (`README.md`, `.gitignore`, `LICENSE`). If a root change is needed, write it as a request in `docs/app/RootChanges.md` and continue.
- **You never run git write commands.** No `git add`, `git commit`, `git push`, `git tag`, `git branch`, `git checkout -b`, `git stash`, `git reset`. Read-only git (`git status`, `git diff`, `git log`) is allowed. Never run `/gstack-ship`, `/gstack-land-and-deploy`, `/gstack-canary` or any deploy command. I run all git operations myself.
- No em dashes or en dashes anywhere: code, comments, docstrings, docs, test names, error messages. Use a colon, comma, full stop, parentheses or the word "to".

## 2. The part protocol (how every phase is delivered)

Every phase is split into parts (A, B, C, ...). Each part is a small, working, tested unit that I commit and push on its own. For **each part**:

1. Implement only that part's scope. Do not start the next part's work.
2. Run the checks: `ruff format`, `ruff check`, `pytest`. All must pass. Nothing is "done" with a failing or skipped test that was not skipped before.
3. Run `/ponytail:ponytail-review` on the uncommitted diff. Fix every finding that is inside this part's scope. List any finding you chose not to fix, with one line of reasoning.
4. Update the docs listed in section 6.
5. Run the attribution scrub from section 1.
6. **STOP** and print this report, then wait:

```text
PART <phase>-<letter> COMPLETE: <part title>

Files changed:
<output of: git status --short>

Checks:
- ruff format: <result>
- ruff check: <result>
- pytest: <N passed, M failed, K skipped>

ponytail-review: <summary; anything deliberately not fixed and why>

Docs updated: <list>

Suggested commit:
<type>(<scope>): <imperative summary, max 72 chars>

<body: 1 to 3 lines on what changed and why, wrapped at 72>

Next: <next part id and title>
```

7. Do not continue until I reply `next`. When I reply `next`, first run `git status` to confirm the previous part was committed (the working tree for that part should be clean), then start the next part.

Commit message rules: Conventional Commits (`feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `build`), lowercase scope from {`backend`, `parser`, `api`, `store`, `jobs`, `polarity`, `report`, `annotator`, `docs`}, imperative mood, no trailing period, no attribution lines, no emoji.

## 4. Libraries

Pin exact versions in `requirements.txt` / `requirements-dev.txt` as resolved at install time, and record them in `docs/app/BuildLog.md`.

| Purpose | Allowed | Notes |
|---|---|---|
| PDF text | `pdfplumber` | MIT. Accepts a file-like object, so bytes stay in RAM |
| DOCX text | `python-docx` | Plus stdlib `zipfile` and `xml.etree` for parts it does not expose |
| API (from Phase 2) | `fastapi`, `uvicorn[standard]`, `pydantic` v2, `python-multipart` | |
| Database (from Phase 2) | `sqlalchemy` 2.x, stdlib `sqlite3` | `Base.metadata.create_all()`, no migrations tool |
| Config files | `pyyaml` | `yaml.safe_load` only |
| PDF reports (Phase 3) | `reportlab` | Also used in tests to generate PDF fixtures |
| Tests | `pytest`, `httpx`, `pillow` | Pillow only to draw fixture images |
| Lint/format | `ruff` | |

**Forbidden:** PyMuPDF / `fitz` (AGPL, conflicts with the MIT licence), scikit-learn, any LLM or generative API client, Celery, Redis, Alembic, Postgres drivers, `requests` (use `httpx` if HTTP is ever needed), any ORM other than SQLAlchemy.

Adding any dependency not in this table requires: a one-line justification in `BuildLog.md` and a `/ponytail:ponytail-review` that does not flag it. Prefer stdlib.

## 5. Code rules

- Type hints on every function signature. `from __future__ import annotations` in every module.
- Data types as `@dataclass(frozen=True, slots=True)` unless mutation is required. Pydantic only at the HTTP boundary (Phase 2 onward).
- **Offsets are Unicode code points** into the canonical text, zero-based, `end` exclusive: `source_text[start:end]`. Never locate a span with `str.find`, `str.index` or regex search over the output after offsets are assigned. Offsets are computed while text is assembled.
- **Never normalise Unicode** (no NFC, NFD, NFKC). Never alter characters in the canonical text after offsets exist.
- **Privacy:** uploaded bytes and extracted text never touch disk, logs, exception messages or temp files. Parse from `io.BytesIO`. Errors carry a fixed code and safe metadata only (page number, counts), never document text.
- **Errors:** raise typed exceptions with a fixed machine code from the phase spec. No bare `except:`. No `except Exception: pass`.
- Comments explain **why**, not what. No commented-out code. No TODOs without a matching line in `docs/app/Phases.md`.
- Follow ponytail's Full-level ladder: skip it if not needed, then stdlib, then an existing dependency, then the smallest new code. No speculative abstraction, no plugin systems, no base classes with one subclass.

## 6. Docs to update in every part

Not just the BuildLog. Every part updates all that apply:

| File | Update when | What |
|---|---|---|
| `docs/app/BuildLog.md` | Every part | Date, part id, files changed, commands run, test counts, pinned versions added, decisions, blockers, exact next action |
| `docs/app/Phases.md` | Every part | Tick the finished part; adjust later parts if scope moved |
| `docs/app/Architecture.md` | Any change to folder layout, modules, data flow, public types or dependencies | Keep the tree, flow and contracts true to the code |
| `docs/app/ParserContract.md` | Any change to parser output (Phase 1 onward) | The exact output format Tanishq's core consumes |
| `docs/app/API.md` | Any endpoint change (Phase 2 onward) | Method, path, request, response, errors |

`BuildLog.md` is created in the first part if it does not exist. It is the project memory: append, never rewrite history.

Prose in docs goes through `copywriting`, then `copy-editing`, then `stop-slop` before the part is reported complete.

## 7. Skills and commands, and when to use them

Before the first part of each phase, run:
```bash
ls ~/.claude/skills ~/.claude/commands 2>/dev/null
```
Confirm every skill below exists. If one is missing, say so in the part report and continue without it. **Never guess a skill name.**

| When | Skill or command | Purpose |
|---|---|---|
| Start of each phase, before any code | `/gstack-plan-eng-review` on the phase spec | Catch design flaws before building. Report findings; do not rewrite the spec without asking me |
| Throughout | ponytail at **Full** level | Over-engineering brake on every decision |
| A test fails and the cause is not obvious in two attempts | `/gstack-investigate` | Root-cause before patching. Never weaken a test to make it pass |
| End of every part | `/ponytail:ponytail-review` on the uncommitted diff | Over-engineering review (required step 3 of the part protocol) |
| End of a phase that handles uploads, sessions or file parsing | `/gstack-cso` | Security review: path traversal, zip bombs, resource exhaustion, data leakage in logs |
| End of every phase | `/coderabbit:code-review` scoped to the phase (`--base-commit <commit before the phase started>`) | Correctness bugs in the local commit range; it opens no PR. It takes 7 to 30 minutes; run it once per phase, not per part |
| End of every phase | `/gstack-review` | Final pre-landing review of the whole phase diff |
| Architecture.md updates at the end of a phase | `graphify` | Regenerate the module/call graph so Architecture.md matches the code |
| Any docs prose | `copywriting`, then `copy-editing`, then `stop-slop` | In that order |

Phase-end reviews happen after the last part's report. Put their findings in a short `PHASE <n> REVIEW` report with suggested fix commits, each following the part protocol.
